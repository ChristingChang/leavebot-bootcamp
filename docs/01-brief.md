## 問題與證據

好日子科技的員工目前用訊息送假單，送出後**不知道有沒有登記成功**，也沒有地方查自己的申請和狀態（來源：03-LEAVEBOT「情境」）。

待確認的前提（題目情境沒有提供，尚未核實）：

- P-1：訊息假單會造成漏登或重複確認，增加員工與管理者的往返成本。影響的頻率和規模**未量測**。
- P-2：員工願意改用表單，並以「我的假單」列表作為登記成功的依據。
- P-3：本題的請假規則（工作日計算、半天限單日）符合公司實際規章。03-LEAVEBOT 註明正式採用前須由人事確認。

## 目標與成功判準

### G-01｜員工送出假單後，能立即確認申請已登記並看到狀態

- 怎麼判斷：選一位員工並填寫合法假單，送出後畫面顯示成功；「我的假單」出現這筆申請，狀態是 `pending`（待審核），天數由系統計算；重新整理後資料仍在。這條操作可重做，也有對應的自動化驗收測試。
- 目前基準與目標：基準**未量測**（沒有訊息假單漏登率或查詢次數的資料）。這次的代理證據是驗收操作與 TC 全部通過；正式成效要等上線後再收集。

### G-02｜不合法的申請被拒絕，且不留下資料

- 怎麼判斷：缺必填欄位、員工不存在、假別或時段不合法、結束日期早於開始日期、半天假跨日、區間內沒有工作日、理由超過 200 字，這些情況都由後端拒絕。前端顯示看得懂的錯誤，資料庫筆數不變。
- 目前基準與目標：基準不適用（現況沒有系統驗證）。目標是代表性拒絕案例的 TC 全部通過，並人工操作至少一條拒絕路徑。

### G-03｜員工只看到自己的假單

- 怎麼判斷：切換所選員工後，列表只顯示該員工的申請，不混入其他人的假單。
- 目前基準與目標：基準不適用。目標是對應的 TC 通過，並以兩位員工人工交叉核對。

## 範圍與非目標

本次交付一條可驗收的表單主線，使用者是好日子科技的員工。核心情境如下：員工從下拉選單選擇自己（沒有登入），填寫假別（`annual`／`personal`／`sick`）、開始與結束日期、時段（整天／上午／下午）及理由後送出。後端負責驗證、計算天數（只計週一到週五；整天算 1 天，上午或下午算 0.5 天；半天限單日），以 `pending` 狀態存進 SQLite。「我的假單」依所選員工列出申請。規模控制在 2–3 個 User Story、AC ≤ 10、FR ≤ 10、TC 6–12。

| ID    | 這次不做                       | 理由與重看時機                                           |
| ----- | ------------------------------ | -------------------------------------------------------- |
| NG-01 | 登入與身分驗證                 | 課堂主線以下拉選單代替；做 C1 主管操作時再討論身分       |
| NG-02 | 主管核准／駁回、狀態轉換       | 新假單固定 `pending`；主線驗收後可排 C1                |
| NG-03 | 特休額度、國定假日、同組人數   | 需要額外資料與規則；主線驗收後可排 C2、C3                |
| NG-04 | 附件                           | 不在基本範圍；沒有重看時機                               |
| NG-05 | 重複或重疊假單的後端去重       | 決策 D-3：只用前端鎖按鈕防止連點；真實重疊需求出現時再議 |
| NG-06 | LLM 解析、前端框架、部署、CORS | STACK 固定技術邊界；C4/C5 另開挑戰票                     |

## 限制、假設、風險與決策

- 限制：
  - 技術固定為 FastAPI + HTML/CSS/原生 JS + SQLite（標準庫 sqlite3）+ pytest。前端只呼叫相對路徑 `/api/...`，不開 CORS（來源：04-STACK）。
  - 驗證在後端進行；狀態與天數不接受客戶端指定；SQL 使用參數；理由以 `textContent` 呈現（來源：03-LEAVEBOT、AGENTS.md）。
  - 「今天」從 `LEAVEBOT_TODAY` 讀取，課堂固定為 `2026-10-12`；測試使用暫存資料庫並注入固定時鐘（來源：04-STACK）。
  - 時間只有第二天一天：上午完成規格，下午實作與驗收（來源：02-WORKFLOW）。
- 假設：
  - A-1：員工名單是預先提供的固定資料（種子資料），本次不提供管理介面。若不成立，需另開名單維護需求。SRS 階段由小組確認名單的來源與格式。
  - A-2：「200 字」以字元數計算（全形與半形各算 1），並先去掉前後空白再計算。若人事要求其他計法，會影響驗證規則與 TC。**已於 2026-10-28 由小組確認**（PRD Q-1），另定只含空白的理由視為未填；見 SRS FR-07。
  - A-3：P-1～P-3 未經實際使用者或人事核實。若不成立，G-01 的業務價值需要重估，但課堂交付不受影響。正式採用前由人事確認。
- 風險：
  - R-1：不去重，可能留下內容相同的重複假單（例如鎖按鈕前已重新整理、或從兩個分頁送出）。後果是列表出現重複筆數。處理：接受此風險，並在 SRS 註明；由小組在驗收時觀察。
  - R-2：接受過去日期，可能讓員工誤填成過去的日期。後果是登記錯誤的假單，而本次沒有撤回功能。處理：接受此風險；成功畫面顯示日期與天數供員工自行核對。
  - R-3：下午的變更練習會把理由上限從 200 改為 100（`issues/002-reason-limit.md`）。若規格把 200 寫死在多處，修改時容易漏改。處理：SRS/SDS 讓上限只在一處定義，TC 引用規則編號。由小組負責。
  - R-4：拒絕路徑若只在前端檢查，可能被繞過並存入不合法資料。處理：所有規則都由後端驗證，TC 以 API 層級驗證「拒絕時不存檔」。
- 待決：**沒有阻塞核心流程的待決項。** 三項小組決策已於 2026-10-28 確認（見下節）。A-1、A-2 屬於規格細節，在 SRS 階段（卡 C）由小組定義，不阻塞 Brief。

## 小組決策（2026-10-28 卡 A 訪談確認）

| ID  | 問題                 | 決定                                   | 理由                                                                         | 對規格的影響                                                                   |
| --- | -------------------- | -------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| D-1 | 理由是否必填與長度   | **選填，最多 200 字**            | 補登或私人原因不一定要說明；保留上限，避免過長輸入，也作為下午變更練習的基準 | 空白理由可以送出；超過 200 字由後端拒絕且不存檔；上限只在一處定義              |
| D-2 | 是否接受過去日期     | **接受**                         | 員工需要補登已發生的假，例如病假                                             | 不以「今天」拒絕開始日期，其他驗證照常；TC 用固定時鐘含一筆過去日期的成功案例  |
| D-3 | 重複送出的使用者回饋 | **不自動去重；送出期間鎖住按鈕** | 防止連點造成重複送出，又不必定義「相同假單」或處理重疊判斷                   | 請求進行中停用送出按鈕並顯示送出中，完成後解鎖並顯示成功或錯誤；後端不比對重複 |
