## 範圍、風險與策略

這次最怕失敗的路徑有兩種：
- 員工送出後畫面顯示成功，資料卻不對，例如天數錯、狀態不是 `pending`、被其他員工看到。
- 申請被拒絕了，資料卻偷偷存下來。

策略分三層：
- **API 驗收測試（主力）**：成功、拒絕、資料不變、員工隔離、資料庫故障，都在這一層驗。這是前後端的實際接縫，也能直接查筆數。
- **單元測試**：只用在邊界多、算法純的地方，也就是天數計算與理由規則。
- **人工瀏覽器操作**：驗自動化難以涵蓋的體驗，包括連點、畫面上的文字安全、重啟服務。

高風險項目：

- **拒絕仍存檔（高）**：會留下錯誤假單。以 API 測試驗證，每個拒絕案例都比對送出前後的筆數；對應 NFR-01、TC-03～TC-06、TC-08、TC-10、TC-11。
- **天數算錯（高）**：週末或半天算錯，假期紀錄就錯。以單元測試覆蓋多個邊界，再用 API 驗主案例；對應 FR-06、TC-01、TC-02、TC-07。
- **客戶端指定狀態或天數（高）**：可能繞過審核或竄改天數。以 API 測試驗證，因為只有 API 能送出畫面不會送的欄位；對應 FR-08、TC-08。
- **列表混入他人假單（高）**：個資外洩，也會讓員工看錯。以 API 測試驗證；對應 FR-09、TC-09。
- **資料庫故障卻顯示成功（中）**：員工會以為已登記，這正是本題要解決的問題。以 API 測試搭配替身模擬故障；對應 NFR-01、TC-11。
- **理由字數邊界與空白處理（中）**：合法的被拒，或過長的被收。以單元測試覆蓋，另加一個 API 案例；對應 FR-07、TC-10。
- **理由含 HTML 被渲染（中）**：可能造成 XSS。在瀏覽器人工確認，API 驗證原樣讀回；對應 NFR-02、TC-10、TC-12。
- **連點重複送出（中）**：產生重複假單。只能人工驗證；對應 AC-01.4、FR-10、TC-12。
- **重新整理或重啟後資料消失（中）**：承諾失效。以 API 驗證（同一個資料庫檔、新的 client），重啟則由人工操作；對應 NFR-03、TC-01、TC-12。

**不測範圍（小組已於 2026-10-28 接受；講師可調整）：**

1. （已移入 TC-03 子案例 f，2026-10-28）API-03 回 400（本文不是 JSON）。
2. 讀取 API 遇到資料庫故障回 500：只測寫入故障。
3. 真實資料庫的交易回滾：TC-11 讓寫入在 INSERT 之前就失敗；寫入只有一個 INSERT，風險低。
4. AC-01.4（連點只送一次）與 NFR-03（重啟後仍在）沒有自動化，只有 TC-12 的人工證據。
5. 效能（NFR-06）：待量測，沒有門檻，不測。
6. 模型評測與注入評測：這次沒有 LLM 功能。

## 環境、資料與判定方式

- **執行環境：**
  - 本機 macOS，repo 根目錄的虛擬環境 `.venv`，Python 3.12.14（2026-10-28 確認）。
  - 套件依 `course/01-上課/05-constraints.txt` 安裝，例如 fastapi 0.162.0、starlette 1.10.0、httpx 0.28.1、pytest 9.1.1、uvicorn 0.54.0。這組版本是在 Windows／Python 3.12.9 上驗證過的；**在本機 macOS 上尚未驗證**，第一次執行時要記錄實際結果。
- **執行指令：**
  - 安裝：`.venv/bin/python -m pip install -c course/01-上課/05-constraints.txt -e ".[dev]"`。
  - 測試：`.venv/bin/python -m pytest`。不可假設 shell 已啟用 venv。
  - 啟動服務（人工驗收用）：`.venv/bin/python -m uvicorn app.main:app --app-dir backend --reload`，再開 `http://127.0.0.1:8000/`。
- **測試檔位置（預定）：**
  - API 驗收：`backend/tests/acceptance/test_submit_leave.py`。
  - 單元：`backend/tests/unit/test_leave_rules.py`。
  - 每個業務測試都標註 `@pytest.mark.req("TC-xx", "AC/FR 編號")`。
- **隔離資料庫：**
  - 每個測試用 `monkeypatch.setenv("LEAVEBOT_DB", str(tmp_path / "test.db"))`，再以 `with TestClient(app)` 觸發初始化（SDS「測試注入方式」）。
  - 測試不讀寫 `backend/data/leavebot.db`。
  - 驗證方式：記錄開發資料庫檔案在跑測試前後的修改時間；檔案不存在時，確認跑完後仍不存在。
- **可重建資料：**
  - 每次初始化都建出相同的三位種子員工（E001 王小明、E002 李小華、E003 陳小美），假單 0 筆。
  - 其他前置資料由測試自己透過 API 建立。
- **固定時鐘：** 主線規則不讀「今天」（D-2、Q-8），所以不需要注入。AC 裡的 2026-10-12 只是情境描述，不影響任何預期值（SDS）。
- **判定方式：**
  - 預期值全部來自規格與人工算例，**不呼叫** `count_leave_days` 或 `validate_leave_request` 來算答案。
  - 錯誤只斷言 `errors` 中「包含」預期的 (`field`, `code`)，不斷言順序或訊息全文（SDS）。
  - 每個拒絕案例都要同時斷言兩件事：錯誤內容，以及查列表得到的筆數與送出前相同。
  - `days` 以數值比較（`2 == 2.0`）。
- **外部依賴替身：** 只有一個：TC-11 用 `monkeypatch.setattr(db, "insert_leave", ...)` 模擬資料庫故障。

**合法基底**：多個 TC 會以這筆請求為底稿，再修改部分欄位。

```json
{"employee_id": "E001", "leave_type": "annual", "start_date": "2026-10-16", "end_date": "2026-10-19", "period": "full_day", "reason": ""}
```
