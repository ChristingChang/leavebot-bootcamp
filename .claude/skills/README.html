/to-tickets — 依成果拆票

通用流程：工作分解。

從目標、已定規格、期限與團隊容量出發，先提出整組可交付成果和真實阻塞關係，再依使用者取捨定票。太大的拆、只能一起驗收的合；票數沒有預設答案。

每張票以結果命名，寫明可由別人檢查的完成條件、必要背景及依賴。優先做薄的端到端切片；必要的環境或研究工作可獨立成票。

你打/to-tickets
並說明目標、限制與希望的拆票粒度。

只有你打才跑

/tdd — 紅綠循環

通用流程：實作。

一次只做一個行為。先寫一個會失敗的測試，確認它因為你預期的原因失敗，再寫剛好能過的程式，然後才整理。不要先把整張票的測試一次寫完。

在專案既有的公共接縫寫測試，沿用其測試工具和追溯慣例。完成前執行專案要求的檢查並報告結果。

你打/tdd
並指出要實作的行為。

你打，或它自己接

/diagnosing-bugs — 紅燈原因不明

通用流程：除錯。

先有一條幾秒內能穩定變紅的指令，再談原因。分類：產品回歸、時好時壞、環境問題。然後縮小、有已知好版本就 git bisect、一次只驗一個假說、用輸出證明、修原因、補一個修之前會紅的測試。探針輸出裡的金鑰先遮掉。

找不到能抓到問題的接縫時，把它作為設計問題記錄並提出。

你打/diagnosing-bugs
附上失敗的指令和輸出。

你打，或它自己接

/handoff — 換人、換工具、換目錄

通用流程：交接。

寫一份給下一個全新對話的交接，放在系統暫存目錄，不進這個 repo。內容是進度、已經做的決定和為什麼、下一步、已知的坑、建議接著叫哪些技能。規格和票用路徑指過去。金鑰抹掉。
