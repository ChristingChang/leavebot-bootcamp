測試規劃、案例與 AI 評測的分工

概念回答的問題本課程落點
原作者 test-blueprint測試分哪些層、在哪些接縫驗、何時在 CI 執行？其中的分層、接縫與追溯判斷融入 docs/06-test-plan.md；不照搬它另建的藍圖、CI 與狀態檔。
原作者 uat-cases使用者要用哪些案例驗收？每個案例的編號與期望結果是什麼？案例設計與凍結編號原則融入 06；課程的 TC-xx 同時涵蓋驗收、系統、整合、單元案例，範圍比原作者的 UAT 清單廣。
TC-xx這一則案例在驗哪條 AC／FR／NFR？寫在 06 的測試案例與追溯矩陣；D2 的 pytest 用 @pytest.mark.req 指回它，模型依規則注入假實作。
I4 AI eval整批口語請假句子的解析準確率有沒有達門檻？這是 LeaveBot 專案特有的驗證。I4 依 06 的規則生成腳本，逐句用 fixture 呼叫 POST /api/parse，比較欄位並報準確率；不放在通用主幹，也不是另一套 TC 編號。

TC 要另外一支技能嗎？目前不用。/to-test-plan 定案例與編號；/implement 配合 /tdd 寫並跑測試；最後按案例核對結果、更新追溯。這最後一格是工作與檢查點，不是新的 slash 指令。若專案需要獨立的人工作業驗收清單，才考慮另用原作者的 uat-cases。

文件何時出現？規格、架構、測試計畫分別在對應技能執行時寫出，拆票前已有測試案例。右欄是通用文件角色，實際路徑由專案決定；本課程映射到 docs/01–06。目前這個工作樹尚未建立 docs/；skills/ 存的是做法，並非已完成的文件。

LESSONS.md 是什麼？它是這個 repo 的經驗紀錄，存偏差、誤解、踩坑，不是每個專案都必備的主規格，也不取代測試計畫。

  • implement：單票建置

你可以直接叫；任務符合技能說明時，agent 也可能主動套用：

  • writing-for-agents、writing-hooks：協作規則

hook 另由 .claude/settings.json 在符合的工具事件自動觸發，不需要叫 skill。技能描述的是工作方法，hook 執行的是檢查。想看每支的具體用法，往下跳到第 5 區。

/tdd — 一張票的紅綠循環

通用流程：實作。

一次只做一個行為。先寫一個會失敗的測試，確認它因為你預期的原因失敗，再寫剛好能過的程式，然後才整理。不要先把整張票的測試一次寫完。

測試打在別的模組會呼叫的接縫上（多半是 docs/05-sds.md 的 API），放在 backend/tests/<layer>/。每個測試標 @pytest.mark.req("TC-xx", "...")。模型只注入假實作，不打真的 API。

票結束前：跑完整 pytest 並貼結果、更新 docs/06-test-plan.md 追溯矩陣、有偏差就寫 docs/LESSONS.md。

你打/clear
然後 /tdd，並指那張票，例如 issues/001-i1-first-slice.md

你打，或它自己接

/diagnosing-bugs — 紅燈原因不明

通用流程：除錯。

先有一條幾秒內能穩定變紅的指令，再談原因。分類：產品回歸、時好時壞、環境問題。然後縮小、有已知好版本就 git bisect、一次只驗一個假說、用輸出證明、修原因、補一個修之前會紅的測試。探針輸出裡的金鑰先遮掉。

找不到能抓到這個 bug 的接縫時，寫進 docs/LESSONS.md，拿回 SAD / SDS 討論。

你打/diagnosing-bugs
附上失敗的指令和輸出。
