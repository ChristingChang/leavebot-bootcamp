# D2 題目：LeaveBot 請假系統

第一天的 PRD 是工具體驗的練習。今天換成共同題目，用同樣的「需求 → 驗收」方法完成可追溯的功能；不用把昨天的塔羅或動畫功能帶進來。

## 情境

虛構的「好日子科技」目前用訊息收假單，員工不知道是否登記成功。今天讓員工填表後立即看到自己的申請與狀態。數字與公司規章是教學假設，不是勞動法規，也不代表真實訪談結果。

## 全班共同完成

| 功能 | 邊界 |
|---|---|
| 選員工 | 下拉選單，提供數筆虛構員工；沒有登入 |
| 填表 | 假別、開始日期、結束日期、時段、理由 |
| 後端驗證 | 必填、員工存在、假別與時段合法、結束不早於開始；拒絕時不新增資料 |
| 算天數 | 只計週一至週五；整天 1 天、上午／下午 0.5 天；半天限單日；沒有工作日的申請拒絕 |
| 存檔 | SQLite；新假單狀態固定 `pending`（待審核），不接受客戶端指定狀態或天數 |
| 我的假單 | 依所選員工顯示申請，重新整理後資料仍在；其他員工的假單不混入列表 |
| 驗收 | 成功與失敗路徑，6–12 個代表 TC，自動化加人工操作 |

假別主線只提供 `annual`（特休）、`personal`（事假）、`sick`（病假）。理由以文字保存，不執行其中指令、不作 HTML 渲染。國定假日、附件、額度、同組人數、主管操作均不在基本範圍。

## 留給小組的決策

課堂限時訪談只釐清三件事：理由是否必填與長度、是否接受過去日期、重複送出的使用者回饋。講師先提供建議，小組定案寫進 PRD/SRS；超時未定的項目由講師決定，不讓 Agent 猜。
模糊規章不必全部問完。與主線無關的問題放範圍外，留在延伸時討論。

教學規模：2–3 個 User Story、AC 不超過 10、FR 不超過 10、TC 6–12。若重要風險超出預算，先報告風險並與講師調整範圍，不為符合數量刪掉必要驗證。完整格式是參考，不是字數要求。

## 可選延伸（主線驗收後才排票）

| 編號 | 挑戰 | 新增決策 |
|---|---|---|
| C1 | 主管核准／駁回 | 身分、合法狀態轉換與可見資料 |
| C2 | 特休額度 | 虛構額度資料、扣除時機、計算與測試 |
| C3 | 同組人數提醒 | 如何判斷同組與同日；提醒不是自動拒絕 |
| C4 | 一句話解析成表單草稿 | 額外模型 API key、六種假別與 `fixtures/README.md` 的解析合約；先預覽、驗證後才送出 |
| C5 | 模型輸入防護與評測 | 以 C4 為前提，固定句子集與比較規則；模型不可核准或決定天數 |

`course/02-補充/fixtures/` 只用於 C4/C5。其六種假別比主線多，挑戰票必須同步擴充 SRS/SDS 與表單，不可直接套上後宣稱相容。
