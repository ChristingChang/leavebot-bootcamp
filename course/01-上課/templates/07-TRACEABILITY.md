# 追溯：一條需求怎麼接到結果

編號是跨文件查找的索引，適合用表格核對：

| 編號 | 意義 | 定義位置 |
|---|---|---|
| `G-xx`、`NG-xx` | 目標、非目標 | Brief |
| `US-xx`、`AC-01.1` | 故事、驗收條件 | PRD |
| `FR-xx`、`NFR-xx` | 系統行為、品質要求 | SRS |
| `API-xx`、`UI-xx` | 介面與畫面接縫 | SDS |
| `TC-xx` | 測試案例 | Test Plan |

有真正架構取捨時才新增 ADR 編號。

```text
G → US → AC → FR／NFR → API／畫面 → TC → 測試或人工證據
```

編號發出後不重用，作廢留著註記。需求定義放對應文件，後續引用不複寫整份。每個 G 都要有 US／AC，每條 AC 都要有 FR／NFR 和驗證結果；SDS 契約及 TC 連到實際受影響的需求，不為了畫出一條直線而硬連無關項目。
業務測試標 `@pytest.mark.req("TC-01", "AC-01.1", "FR-01")`。每張票結束更新 `docs/06-test-plan.md`，小組親手抽查至少一條；有 marker 不代表測試真的驗到該行為，還要讀斷言。

找不到 TC、找不到測試、沒有執行證據，都是缺口。未驗證項明記原因，不能用 ✅ 代替實際結果。
課程不要求四層測試一一成對；選能抓出問題的公開接縫。完整 V-model 可課後參考 IT 設備借用範例。
